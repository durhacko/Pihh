## 1. Scope and evidence rules

The feature is persistence, not simulation. Almost everything here is decided by deterministic pass/fail tests. The only flight evidence needed is that a loaded show reaches the swarm through the **existing** operator pathway, with determinism unchanged. Flight quality is covered by the base and Gemini evaluations.

| Kind | Where it runs | What it may establish | Permitted wording |
|---|---|---|---|
| **Offline** (unit, UI, scans, build) | Core `npm run check`, or a scan over `dist/`; no network, no database | Validation, serialisation, UI states, load scheduling, determinism, isolation, bundle hygiene | "MDB-Txx passes on commit X" |
| **Mocked service** (integration) | The optional service's own package, in process, with a fake `ShowsRepository` | HTTP behaviour, statuses, error envelope, idempotency logic, limits | "Against a fake repository, the service returns …". **Never** "saved to Atlas" |
| **Live** | The service against a separate Atlas test database (§4) | Real persistence, unique index, BSON types and failure behaviour | "Read-after-write verified against Atlas on date D, `_id` …" |
| **Acceptance** | A person in a browser, following §5 | William's whole workflow | Only with the §5 evidence attached |

Rules:

1. **No cloud claim from a mock.** William: "Do not claim live Atlas verification without an actual read-after-write test" (§10).
2. **Core checks stay offline.** Mocked-service and live tests never run under the root `npm run check` or `bash scripts/check.sh`. They live in the shared optional gateway's package, `integrations/gateway/` (independently optional `gemini`, `shows` and `tiger` modules; MCR-07, MDB-D4). The server, guard, error helpers, config and health route are the shared gateway skeleton (XI-12), built once by whichever module work package is approved first; the `shows` tests here cover only the shows-specific parts and re-run the skeleton's tests with the shows routes on. The Gemini gateway tests work the same way ([GF §5.8](gemini-formation-evaluation.md#58-gateway-class-a-mode-live-gateway-only-gated-on-gf-d1), provisional: depends on #117).
3. **Live tests are opt-in.** They run only when the test-database environment is set, and never against the demo database. If they are skipped, they are reported as not run.
4. **Validated is not flown, and loaded is not flown.** "Loaded" means "drafts created" for the MVP's **Load as drafts**, or "injections scheduled" for the runner follow-up (MDB-D6).

### 3.1 Validation and serialisation (T01–T10)

One pure validator runs everywhere. It has no DOM and no three.js, and it runs at four call sites: in the app before save and before load, and in the gateway on write and on read ([spec §9](../integrations/mongodb-atlas-show-library.md#9-validation-md-4)). The gateway imports this same module by relative path (decision XI-2, superseding Gemini CR-24): one implementation, not two copies. The module is the pure `src/app/compose/validate.ts` (XI-13; created by P2-WP-30a, or by MDB-WP-02 if 30a has not landed). MDB-WP-02 adds the composition validator to that same file, not to a second module. Every test in this group targets that module.

### 3.3 Idempotency, write protection, limits and secrets (T19–T24)

| ID | Test | Level | Setup | Pass condition | WP |
|---|---|---|---|---|---|
| **MDB-T19** | Duplicate retries | integration | The fake with a unique `operationId`, and `foreignDuplicate` and `vanished`; the app client with a fake transport | The comparison is `requestHash` (spec §7.3, §10.5), not `contentHash`. Same key and same normalised request: `201`, then `200` with the same `id` and `idempotentReplay: true`; one document. Same key and same composition but a new title, a ticked "Store prompt", or a changed `source` or `generator`: `409` `CONFLICT` (reason `IDEMPOTENCY_CONFLICT`). ## 4. Database testing setup

- **Unit and integration:** the fake repository only. No driver connection, no network.
- **Live:** a separate database, for example `encore_test`, never the demo's `MONGODB_DB=encore`.
- **Two principals** (spec §21). Database-level `readWrite` is not the target: it grants update, remove and drop on every collection, and the MVP is append-only. Spec §21 allows it only as a fallback, recorded as a risk, if collection scoping is unavailable.
  - **Runtime:** the service's user holds only a custom role with `find`, `insert` and `listIndexes` on `encore_test.saved_shows` (no update, remove, drop, `createIndex` or `collMod`; collection scoping on the Atlas tier in use is UNVERIFIED, spec §27 item 4, and T37 checks it). On its first successful connection the service confirms the unique `operationId` index with `listIndexes` (spec §11). Until it is confirmed, writes fail closed with `503` `INDEX_MISSING`. It never creates indexes.
  - **Set-up:** a separate admin user runs a one-off set-up script that creates the indexes and the optional `$jsonSchema` validator (`collMod`). It is never in the service's environment.
  - Both have a network access list restricted to the tester's address, with credentials only in the runner's environment (`MONGODB_TEST_URI`, `MONGODB_TEST_DB`; the set-up URI separately). The demo user is a third, separate user on the demo database (spec §21); test runs never use it.
- **Clean per run:** each run prefixes its `operationId`s with a `runId`. In `afterAll`, including after a failure, the set-up principal (the runtime one cannot delete) deletes what the run created and sweeps stale runs older than 24 h, then records that zero of its documents remain.
- **Never in CI:** neither CI nor `scripts/check.sh` sets the test environment. Live latency is an observation, never a target. Quotas and cost depend on the Atlas plan (William §8.4).

## 9. Wording, and inconsistencies noted while writing

**Wording.** The base [rules](evaluation-and-tests.md#8-bias-risks-and-reporting-wording) apply. Say "saved to and retrieved from MongoDB Atlas" only with T38 or T40 evidence. Say "the swarm's gossip disseminates the loaded show", never "Atlas sends the show to the drones". A saved show is not a "recorded run". Do not call the library "offline-capable": only the core simulation needs no network. Do not write "never at run time": the library is used while the simulation runs, never inside the tick loop or a decision path.
